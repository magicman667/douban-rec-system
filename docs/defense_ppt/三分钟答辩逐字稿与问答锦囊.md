## 三、评委老师高频追问 & 满分应答（背下这 4 题就稳了）

1. **问：你们为什么用这么多组件（Hadoop/Hive/Spark/MongoDB/Weaviate），不能全放 MySQL 吗？**
   - **答**：这是工业界典型的多模持久化架构（Polyglot Persistence）：416 万结构化评分与分布式算力交给 HDFS + Hive + YARN/Spark；变长中文短评与高频更新的流式告警交给 MongoDB；14 万部电影的 50 维+512 维高维向量毫秒检索必须靠 Weaviate HNSW 索引，传统关系库完全做不到毫秒级近似检索。
2. **问：你们单部电影建模样本只有一百到三百条，统计可靠吗？**
   - **答**：这是公开豆瓣 MovieData-10M 接口抽样机制决定的（每片上限约 300–400 条）。从统计学看，150–260 条随机抽样对 1–5 星五档比例的标准误约 ±3%，足以稳定刻画口碑一致与两极分化形态；并且我们对低样本片做了**同类型贝叶斯平滑收缩（m=20）**，同时引入**豆瓣全站总评价人数**交叉校验。
3. **问：你们的算法跟课上讲的纯协同过滤（ALS）有什么本质区别？**
   - **答**：我们不是只跑单一 ALS 或手工加权公式，而是升级成了完整三阶段工业架构：第 1 阶段双向量自适应加权 RRF 召回（NDCG +37.8%）；第 2 阶段引入 21 维交叉特征并用 Spark YARN GBT / FM / GBDT+LR / Hist-GBDT 五类经典机器学习精排，在严格防穿越测试集上把 ROC-AUC 从 0.7590 提升到 0.8296（+7.06pp）；第 3 阶段叠加原创非对称分歧防雷，将稳妥用户踩雷率压至 0%。
4. **问：为什么强调“两阶段时序防穿越切分”？**
   - **答**：如果用同一批训练评分既训 ALS 向量、又用 ALS 向量内积去训 GBDT，树模型会直接“记住”训练样本，导致离线虚高（我们实测 ALS 在自身训练集内 AUC 高达 0.9748）。按用户真实打分时间严格切成 Stage-1（训 ALS）、Stage-2（训精排）与封存测试集后，ALS 真实泛化 AUC 回到 0.7601，杜绝任何数据泄露。
